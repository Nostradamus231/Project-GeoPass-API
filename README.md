# GeoSaaS API: Автоматизированный расчёт и генерация паспорта месторождения

Серверная часть микросервисной SaaS-платформы для недропользователей, проектных институтов и геологоразведочных организаций. Сервис автоматизирует камеральную обработку маркшейдерских и геологических данных, выполняет расчёт геометрических и объемных параметров залежи, классификацию запасов и формирование регламентного документа «Паспорт месторождения» в формате DOCX.

---

## 1. Аннотация

Камеральная обработка первичных геологических и маркшейдерских материалов при подготовке «Паспорта месторождения» традиционно выполняется вручную. Геолог или горный инженер переносит координаты скважин и угловых точек горного отвода в ГИС или табличные редакторы, рассчитывает площади полигонов, вычисляет средневзвешенные мощности полезной толщи, определяет запасы сырья и вручную переносит полученные данные в текстовые шаблоны.

Данный процесс сопряжён с рядом критических недостатков:
* **Высокие временные затраты**: оформление одного паспорта занимает от 6 до 16 рабочих часов высококвалифицированного специалиста.
* **Человеческий фактор**: риск механических ошибок при округлении, переносе координат и расчёте средневзвешенных параметров.
* **Несинхронизированность стандартов**: отклонения в оформлении и формулировках регламентных разделов.

**GeoSaaS API** решает указанную проблему путём предоставления REST API, принимающего сырые структурированные данные по контуру горного отвода, координатам и мощностям скважин, а также показателям качества сырья. Сервис производит мгновенный валидированный расчёт и возвращает готовый к печати и утверждению документ регламентного образца.

## 2. Актуальность и бизнес-обоснование

### 2.1. Количественная модель снижения OPEX

Внедрение микросервиса автоматической генерации паспортов месторождений напрямую сокращает операционные расходы (OPEX) недропользователя за счёт высвобождения фонда оплаты труда (ФОТ) ведущих геологов и маркшейдеров.

Определим переменные аналитической модели:
* $S_{\text{hour}}$ — почасовая ставка геолога / маркшейдера (включая налоги и отчисления), ден. ед./час;
* $T_{\text{manual}}$ — среднее время ручной подготовки паспорта месторождения (сверка координат, расчёт площади, мощностей, объёмов, запасов, вёрстка в текстовом процессоре), часов;
* $T_{\text{auto}}$ — время подготовки входного JSON и автоматической генерации через GeoSaaS API, часов;
* $N$ — количество составляемых или обновляемых паспортов/отчётов в год (для группы лицензионных участков, эксплуатационных блоков или карьеров);
* $C_{\text{infra}}$ — годовая стоимость вычислительной инфраструктуры микросервиса, ден. ед./год.

Годовые операционные затраты при ручном подходе:
$$\text{OPEX}_{\text{manual}} = N \cdot T_{\text{manual}} \cdot S_{\text{hour}}$$

Годовые операционные затраты при использовании GeoSaaS API:
$$\text{OPEX}_{\text{auto}} = N \cdot T_{\text{auto}} \cdot S_{\text{hour}} + C_{\text{infra}}$$

Экономический эффект (чистая экономия OPEX в год):
$$\Delta \text{OPEX} = N \cdot (T_{\text{manual}} - T_{\text{auto}}) \cdot S_{\text{hour}} - C_{\text{infra}}$$

### 2.2. Пример расчёта «до/после»

Примем базовые инженерно-экономические допущения (без привязки к конъюнктурным флуктуациям):
* $T_{\text{manual}} = 8$ часов (один полный рабочий день на паспорт);
* $T_{\text{auto}} = 0.25$ часа (15 минут на выгрузку данных из СУРБ/ГИС в API и проверку готового DOCX);
* $N = 60$ паспортов/дополнений в год (холдинг или средняя проектно-геологическая компания с сетью участков);
* $S_{\text{hour}} = C_{\text{FOT}}$ (базовая ставка специалиста);
* $C_{\text{infra}} \approx 0.05 \cdot (N \cdot T_{\text{manual}} \cdot S_{\text{hour}})$ (незначительные затраты на легковесный контейнер).

Снижение трудозатрат:
$$\Delta T = \frac{T_{\text{manual}} - T_{\text{auto}}}{T_{\text{manual}}} \cdot 100\% = \frac{8 - 0.25}{8} \cdot 100\% = 96.88\%$$

Сокращение рабочего времени на один документ составляет более **96%**, что позволяет геологической службе сконцентрироваться на полевом контроле и интерпретации геологоразведочных данных вместо рутинной бумажной работы.

## 3. Архитектура SaaS-сервиса

Сервис построен по принципам чистой слоистой архитектуры и строгой однонаправленности зависимостей.

```
+-------------------------------------------------------------------------+
|                              Клиент (HTTP)                              |
+-------------------------------------------------------------------------+
          |                                            ^
          | POST /generate-passport                    | GET /download/{id}
          v                                            |
+-------------------------------------------------------------------------+
|                                main.py                                  |
|   (Оркестратор FastAPI, CORS, Global Exception Handlers, Uvicorn)       |
+-------------------------------------------------------------------------+
          |
          v
+-------------------------------------------------------------------------+
|                             api_routes.py                               |
|   (Эндпоинты API, трансляция кодов HTTP, файловая отдача FileResponse) |
+-------------------------------------------------------------------------+
         /               |                              \
        v                v                               v
+---------------+  +---------------------------+  +----------------------+
|  schemas.py   |  |      calc_engine.py       |  |    doc_builder.py    |
| (Pydantic v2, |  | (Shapely + NumPy гео-     |  | (docxtpl + Jinja2,   |
|  контракты,   |  |  вычислитель, метрика,    |  |  генерация DOCX,     |
|  валидация)   |  |  запасы, классификация)   |  |  uuid, path safety)  |
+---------------+  +---------------------------+  +----------------------+
```

### Принципы разделения ответственности:
1. **`schemas.py`**: Декларативные схемы запросов и ответов Pydantic v2. Обеспечивает строгую типизацию, проверку граничных условий и запрет паразитных полей (`extra="forbid"`). Не зависит от веб-фреймворка.
2. **`calc_engine.py`**: Чистое геоинженерное ядро на базе Shapely и NumPy. Производит трансформацию систем координат, расчёт полигональной геометрии, статистический анализ мощностей и вычисление балансовых запасов. Не импортирует FastAPI и не знает о механизмах рендеринга.
3. **`doc_builder.py`**: Сервис формирования документов DOCX на основе шаблона и контекста. Инкапсулирует работу с `docxtpl`, управление безопасностью путей (`Path.is_relative_to`) и исключает path traversal.
4. **`api_routes.py`**: Тонкий контроллер, связывающий валидацию, вычисления и сборку документов в единый пайплайн.
5. **`main.py`**: Точка входа приложения, конфигурация ASGI-приложения и централизованная обработка системных и валидационных исключений.

## 5. Методика геоинженерных расчётов

### 5.1. Расчёт площади и периметра
Полигон строится по набору вершин контура $\mathbf{P} = \{(x_1, y_1), (x_2, y_2), \dots, (x_n, y_n)\}$. Замкнутость контура контролируется автоматически библиотекой Shapely (алгоритм формулы шнурования Гаусса):
$$S = \frac{1}{2} \left| \sum_{i=1}^{n} (x_i y_{i+1} - x_{i+1} y_i) \right|$$
где $(x_{n+1}, y_{n+1}) = (x_1, y_1)$.
Периметр $L$ рассчитывается как евклидова длина границы:
$$L = \sum_{i=1}^{n} \sqrt{(x_{i+1} - x_i)^2 + (y_{i+1} - y_i)^2}$$

### 5.2. Проекция географических координат в локальную метрическую систему
Если параметр `coordinate_system` равен `geographic`, координаты интерпретируются как долгота $\lambda$ и широта $\varphi$ в градусах. Для локальных участков месторождений применяется равнопромежуточная проекция относительно географического центроида контура $(\lambda_0, \varphi_0)$:
$$\varphi_0 = \frac{1}{n} \sum_{i=1}^n \varphi_i, \quad \lambda_0 = \frac{1}{n} \sum_{i=1}^n \lambda_i$$
$$x_m = R \cdot \cos(\varphi_0) \cdot (\lambda - \lambda_0) \cdot \frac{\pi}{180}$$
$$y_m = R \cdot (\varphi - \varphi_0) \cdot \frac{\pi}{180}$$
где $R = 6371008.8$ м — средний радиус Земли (IUGG).
*Инженерное допущение прототипа*: данная проекция корректна для компактных лицензионных участков (до 20–30 км в поперечнике), искажения длин и площадей на таких масштабах не превышают долей процента.

### 5.3. Средневзвешенная мощность и показатели вариации
Для набора разведочных скважин с мощностями полезного ископаемого $m_i$ и весами влияния $w_i$:
$$\bar{m}_w = \frac{\sum_{i=1}^k m_i \cdot w_i}{\sum_{i=1}^k w_i}$$
Стандартное отклонение и коэффициент вариации мощности (мера изменчивости пласта):
$$\sigma_m = \sqrt{\frac{1}{k} \sum_{i=1}^k (m_i - \bar{m})^2}, \quad V_m = \frac{\sigma_m}{\bar{m}} \cdot 100\%$$

### 5.4. Подсчёт геологических объёмов и запасов
Геологический объём минерального сырья:
$$V = S \cdot \bar{m}_w \quad (\text{м}^3)$$
Балансовые запасы полезного ископаемого:
$$Q = V \cdot \rho \quad (\text{т}), \quad Q_{\text{kt}} = \frac{Q}{1000} \quad (\text{тыс. т})$$
где $\rho$ — средняя плотность массива сырья (т/м³).

### 5.5. Демонстрационная категоризация запасов
В прототипе реализована условная категоризация запасов на основе плотности сети бурения $D_{\text{bh}} = \frac{k}{S_{\text{ha}}}$ (скважин на гектар) и коэффициента вариации $V_m$:
* **Категория A**: $D_{\text{bh}} \ge 2.0$ скв/га и $V_m \le 15\%$ (высокая детальность и выдержанность);
* **Категория B**: $D_{\text{bh}} \ge 1.0$ скв/га и $V_m \le 25\%$;
* **Категория C1**: $D_{\text{bh}} \ge 0.2$ скв/га и $V_m \le 40\%$;
* **Категория C2**: разреженная сеть или сложная морфология залежи ($V_m > 40\%$).

*Примечание*: данная алгоритмическая категоризация служит демонстрационной инженерной моделью и не заменяет государственную экспертизу запасов (ГКЗ).

## 6. Шаблон паспорта и теги docxtpl

Шаблон паспорта (`templates/passport_template.docx`) формируется автоматически скриптом `create_template.py` и соответствует деловым регламентам технической и маркшейдерской документации:
* **Геометрия страницы**: формат А4, поля: левое — 30 мм, правое, верхнее и нижнее — по 20 мм.
* **Типографика**: базовый шрифт — Times New Roman 12 пт, межстрочный интервал 1,15, выравнивание основного текста по ширине. Заголовки разделов оформлены стилем `Heading 1` (14 пт, полужирный, цвет `#1B365D`), титульное название — стилем `Title` (18 пт, полужирный, заглавные).
* **Титульный блок (первая страница)**: включает название «ПАСПОРТ МЕСТОРОЖДЕНИЯ», наименование участка, вид сырья и реквизитную таблицу «Показатель | Значение» без внутренних вертикальных линий с тонкими разделителями. После титульного блока следует принудительный разрыв страницы.
* **Колонтитулы и нумерация**: титульная страница свободна от колонтитулов (`different_first_page_header_footer = True`). Со второй страницы активируются верхний колонтитул с наименованием сервиса и месторождения, а также нижний колонтитул с динамическими полями Word `PAGE` и `NUMPAGES` в формате «Страница X из Y».
* **Табличные блоки**: шапки таблиц выделены заливкой `#F0F4F8` и зафиксированы для переноса на новые страницы (`tblHeader`). Все числовые колонки выровнены по правому краю.
* **Устранение дублирования**: показатели мощности и запасов приведены один раз в регламентных таблицах разделов 2 и 5 без избыточного текстового повторения.

| `{{ row.thickness_m }}` | `str` | `5,00` | Мощность полезной толщи в скважине (м, 2 знака) |
| `{{ row.weight }}` | `str` | `1,00` | Весовой коэффициент скважины (2 знака) |

## 8. Безопасность и защита данных

1. **Коммерческая тайна и конфиденциальность недропользователей**:
   * Все сгенерированные пользовательские файлы DOCX хранятся во временном каталоге `output/` и **полностью исключены из репозитория Git** через `.gitignore`.
   * Единственный версионируемый файл `.docx` — нейтральный обезличенный шаблон `templates/passport_template.docx`.
2. **Защита от атак обхода каталога (Path Traversal)**:
   * Эндпоинт `/download/{file_id}` строго валидирует строковый идентификатор через парсинг `uuid.UUID`.
   * Резолвинг пути использует каноническую проверку `target_path.is_relative_to(output_dir)`. Запросы вида `/download/..%2Fmain.py` или манипуляции со слешами отсекаются с кодом `404 Not Found`.
3. **Рекомендации для промышленного развёртывания (Production)**:
   * **Аутентификация и авторизация**: внедрение OAuth2 / JWT (Bearer токены) или API-ключей для разделения тенантов.
   * **Жизненный цикл файлов (TTL)**: интеграция фонового планировщика для автоматического удаления DOCX-файлов старше 24 часов.
   * **Объектное хранилище**: замена локального диска на S3-совместимое хранилище (MinIO, AWS S3, Yandex Object Storage) с генерацией подписанных временных ссылок (Pre-signed URLs).
   * **Защита транспортного уровня**: принудительное использование TLS/HTTPS и ограничение скорости запросов (Rate Limiting).

## 10. Ограничения прототипа и Roadmap

### Ограничения текущей версии
* Отсутствие постоянной базы данных (статус и метаданные хранятся stateless/in-memory).
* Упрощенная проекция для географических координат без учета локальных искажений зон Гаусса-Крюгера.
* Алгоритмическая классификация категорий запасов носит индикативный характер.

### Дорожная карта развития (Roadmap)
1. **Мультитенантность и RBAC**: профили компаний, разделение доступа геологов, маркшейдеров и руководства.
2. **Поддержка ГИС-форматов**: прямой импорт контуров и скважин из Shapefile (.shp), GeoJSON, DXF и выгрузок KML/KMZ.
3. **Геостатистическое моделирование**: оценка запасов методами ординарного кригинга (Ordinary Kriging) и триангуляции Делоне без внешних тяжелых ML-зависимостей.
4. **Асинхронные очереди задач**: переход на Celery/Redis для пакетной генерации сотен паспортов месторождений крупных холдингов.
